# D: safe HTTP facts and refresh eligibility

Issue #21. Stacked on C PR #20 (`feat/19-usage-state`). Design reviewed and amended per advisor; implementation pending; no runtime dependency, SDK/version change, automatic merge or release. E's layout/theme/widget options are excluded.

## Safe read outcomes

Add optional structured failure facts to discovery failure and account error outcomes: `scope` (management/provider), `category` (rate-limit/server/network/timeout/auth/http/invalid-response), optional integer HTTP status and absolute `retryAfterAt`. Never retain raw body/header objects, URLs, tokens or arbitrary remote error fields. Existing sanitized human error text and Management-auth rejection protection remain. Provider 401 is not Management rejection.

A pure HTTP helper parses only Retry-After. Accept nonnegative integer delta-seconds or HTTP-date syntax (IMF-fixdate and the two obsolete HTTP date forms), not permissive Date.parse garbage, signed/fractional seconds or nonfinite numbers. Compute the absolute deadline when the response arrives, not when the entire refresh finishes. Dates already due produce no future constraint; zero seconds imposes no future wait. Saturate unrepresentable future delta-seconds at the maximum valid JS Date rather than overflowing or imposing the local cap. Test strict grammar, calendar validity, dates, integer limits and long waits. Inspect only status and Retry-After from outer Management and nested api-call response headers, case-insensitively. Apply valid server Retry-After on any unsuccessful HTTP result, including 503, not just 429.

Reads keep concurrent account queries and stable discovery order. Aggregate maximum deadlines across the entire round; a success does not erase a sibling failure. Once a Management rejection, any outer 429 (even without valid Retry-After), or a future server constraint is observed inside a read, suppress unstarted subsequent discovery/query work across providers; mark skipped account queries `queried: false`, carrying only the safe blocking failure. Already-started concurrent work is not promised to stop. Independent discovery still proceeds after ordinary non-429/non-auth failures without a server wait, preserving B. No-header 429 establishes only local source backoff, never a fabricated server deadline. A skipped discovery (`attempted: false`) preserves pre-begin discovery/account facts and all their attempt/data times; it is represented by source eligibility, not a new discovery failure.

## Minimal session-only policy facts

Extend the existing provider state with optional retry facts: consecutive transient-failure round count, optional `backoffUntil`, and optional provider `serverUntil`. Keep one separate Controller source-level retry record with the same streak/backoff/server fields (not per model or a parallel cache). Actual Management temporary failures, including 429 without valid Retry-After, establish source-level local backoff. They never masquerade as explicit server waits. No raw failures/history/credentials are stored by scheduling policy.

Temporary means network, timeout, 429 or HTTP 5xx; auth, ordinary 4xx, parse errors, successful unknown/empty data and local missing-ID/unavailable conditions are not temporary. Increment at most once per provider round even for many failing accounts. A round containing a temporary failure increments even if other accounts succeeded. Delay = configured refresh interval × 2^(failure count − 1), capped at max(configured interval, 60 minutes), with overflow-safe arithmetic. For provider policy, count only actual `queried: true` provider error outcomes (not outer Management errors or inherited skipped errors); a completed discovery-success round without Management failure can reset its local streak if it has no provider temporary errors, including unknown/empty. For source policy, the read layer reports whether Management requests actually completed and the safe failures from those requests only; an actual completed Management round without temporary Management errors resets source local streak, while any temporary Management failure wins over all same-round successes, regardless of response order. No observations leaves existing policy unchanged. Local backoff is not proof of valid quota. An incomplete/cancelled or ineligible round never updates retry facts.

Take the maximum existing unexpired and newly observed server deadline. No successful round, forced query, model switch, provider toggle or refresh-interval adjustment shortens a known server wait. Provider cache deletion on disable must retain only that provider's live serverUntil within its existing provider record (no historical quota); re-enable within the source still obeys it. Clear all retry facts only on source URL/key boundary change, true reset/logout, session start/shutdown. Preserve B generation/ownership checks before every post-await write. Configuration/provider toggles invalidate work as before, but must not accidentally clear source server constraints.

## One gate, existing queue and periodic schedule

In `performRefresh`, first load/resolve/adopt source and configuration; then filter enabled/requested providers through eligibility before `beginProviderRead`. Effective server deadline is max(source and provider serverUntil); effective automatic gate is max(server deadline, provider backoffUntil, source backoffUntil). Force can bypass only local backoff. Existing rejected Management key stops automatic requests; explicit force may revalidate it, but cannot bypass server wait. `notify` alone is not force. All callers (tick/model/details/r/command/start) use this gate. Recheck at queue execution time, not just enqueue time: a pending force behind a newly rate-limited round is blocked.

Blocked calls resolve immediately, produce no provider HTTP, do not update attempt/results/timestamps/streak, and do not create a waiting queue or timer per caller. Explicit feedback uses the same snapshot. Not being eligible is independent of quota loading/error/unknown state; no fake attempt/failure is recorded.

Keep the current setInterval strategy, not a new retry scheduler. Track the next actual periodic check and its current context/model ownership; timer callback advances this timestamp even if the request gate blocks it. `automaticAllowedAt` and `manualAllowedAt` are deadline constraints, not a promised request. `nextAutomaticCheckAt` describes the existing interval tick, and may precede eligibility. Outside an active periodic schedule/eligible active model/configuration report no automatic plan, not a fabricated retry time. Settings interval changes reset the actual tick anchor and do not shorten server constraints. Display a plan only for the provider matching the current context. Model selection updates timer ownership to the current context without silently creating an extra automatic schedule.

Add detached readonly eligibility facts to the shared snapshot: source/provider server deadlines, effective local-backoff deadline, separate future automaticAllowedAt and manualAllowedAt, and optional actual nextAutomaticCheckAt. Surface concise waiting reason in shared status annotation, and explicit earliest allowed/manual-vs-auto/next automatic check lines in details/status. Manual may be allowed earlier than automatic when only local backoff applies; do not present automatic nextAllowedAt as a universal prohibition.

Reuse C's single repaint-only timeout to wake at the next *future* freshness or visible retry deadline, segmented to the Node timeout maximum. Due deadlines do not reschedule tight loops. Repaint never starts HTTP. Clear timers/owners on source/lifecycle invalidation and model/context changes; no timer keeps a stale context. No additional per-provider retry timeout or account scheduler.

## Regression matrix before implementation

1. Strict Retry-After integers/date formats/invalid dates/zero/past/fraction/negative/huge values; safe outer/nested failure facts, 429 and 503; no raw response/credential exposure.
2. Provider cooldown isolated from others; Management discovery or api-call wait blocks same-source providers and unstarted work; two concurrent deadlines choose max independent of completion order.
3. Fake clock: backoff starts at interval, doubles/caps; one increment per round and partial failure retained; unknown/empty/complete nontransient round resets local streak without inventing valid-data success.
4. Every trigger and queued force obey server wait; repeated blocked refreshes settle with no HTTP, no pending accumulation and no attempt/streak changes; manual force bypasses only local backoff; Management/provider auth remain distinct.
5. Source/key/session/reset clear old constraints; model changes and disable/re-enable do not bypass live waits. Aborted/late old results cannot establish waits in the new source. Interval change cannot shorten server wait.
6. Source Management 429 without a header blocks cross-provider automatic requests but allows force; skipped/inherited failures do not add streaks; mixed source successes/failures are order-independent. Pure state clone/apply/begin operations must preserve detached retry fields, including server-only records retained across disable/re-enable.
7. Shared views show separate earliest allowed and next check; local backoff says force is available. No automatic schedule means no advertised automatic request. Status/snapshot and deadline expiry are read-only; very long waits segment repaint without overflow or busy spin.
8. Existing B/C tests retain isolation/freshness assertions. Intentional immediate retries after transient failure use explicit force or clock advancement, not weakened assertions.
